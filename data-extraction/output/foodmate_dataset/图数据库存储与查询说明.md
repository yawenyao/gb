# GB 2760 图数据库存储与查询说明

本文档说明：图数据库（Neo4j）如何存储食品添加剂与食品分类的使用关系、如何查询、双向交叉查询的原理，以及标准中的层级/继承关系在数据中的体现与研判方式。

---

## 一、图模型概览

### 1.1 节点类型

| 节点标签 | 含义 | 主键 | 主要属性 |
|----------|------|------|----------|
| **Additive** | 食品添加剂（表 A.1 中的一条） | `faid`（数字） | nameCn, nameEn, cns, ins, function |
| **Category** | 食品分类（表 A.2 中的一条） | `categoryCode`（字符串，如 "01.05.03"） | categoryName, limitId |

### 1.2 关系类型

| 关系类型 | 方向 | 含义 | 关系属性 |
|----------|------|------|----------|
| **USED_IN** | Additive → Category | 该添加剂可在该食品分类中使用 | foodCategoryCode, foodName, **maxUsage**, remark, usageType, residueNote |

即：**（添加剂）-[:USED_IN]->（食品分类）**，一条边表示「该添加剂在该分类下有一条使用规定（含最大使用量/备注等）」。

**单位信息**：是 **USED_IN 关系的属性**。单位不单独建属性，而是写在 **maxUsage** 的字符串里（如 `"0.025 g/kg（仅限果味饮料）"`、`"按生产需要适量使用"`）。若需在查询或展示时单独用单位，可从 maxUsage 中解析，或在导入时额外增加关系属性如 `unit`（如 `"g/kg"`）。

### 1.3 图结构示意

```
(Additive {faid:1, nameCn:"阿拉伯胶"})-[:USED_IN {maxUsage:"按生产需要适量使用", ...}]->(Category {categoryCode:"01.01.03", categoryName:"调制乳"})
(Additive {faid:1})-[:USED_IN]->(Category {categoryCode:"01.02.02", ...})
...
(Additive {faid:2})-[:USED_IN {maxUsage:"0.015 g/kg", usageType:"最大使用量"}]->(Category {categoryCode:"01.02.02", ...})
```

**层级**：数据集与图库已支持分类层级。实体表 `entities/categories.json` 含 `parent_category_code`；导入时创建 **BELONGS_TO** 边（子分类 → 父分类），便于按上级/路径查询。**本级/上级/GMP**：关系 **USED_IN** 上增加属性 **source**（direct / parent / gmp），便于按「本级允许」「上级允许」「适量使用」分组展示。

## 二、数据如何进入图库

### 2.1 数据来源

- **实体**：`entities/additives.json` → Additive 节点；`entities/categories.json` → Category 节点。
- **关系**：`relations/additive_usage.json` → USED_IN 边。该文件为**扁平表**，每行一条「(faid, food_category_code, max_usage, remark, usage_type, residue_note, **source**, **unit**)」。**source** 来自爬虫 limit 页解析（本级/上级/GMP），**unit** 从 max_usage 中提取；导入时一并写入边属性。

### 2.2 导入逻辑（Neo4jDataLoader）

1. 清空图中已有数据（可选）。
2. 遍历 `entities/categories.json`，为每个分类创建 `Category` 节点（categoryCode, categoryName, limitId）。
3. 遍历 `entities/additives.json`，为每个添加剂创建 `Additive` 节点（faid, nameCn, nameEn, cns, ins, function）。
4. 遍历 `relations/additive_usage.json`：对每一行，若该行中的 `food_category_code` 尚无对应 Category 节点则先创建，再创建一条从对应 Additive 到该 Category 的 USED_IN 边，属性来自该行（max_usage, remark, usage_type, residue_note, **source**, **unit**）。
5. 建立分类层级：读取 `entities/categories.json` 中的 `parent_category_code`，为每个有父的分类创建 **(子 Category)-[:BELONGS_TO]->(父 Category)**。

因此，图库中的边与 `additive_usage.json` 的行一一对应，且**包含 source（本级/上级/GMP）与 unit**；分类之间**包含 BELONGS_TO 层级关系**，可实现按「本级/上级/GMP」分组展示与按层级查询。

## 三、如何查询

### 3.1 按添加剂查：该添加剂能在哪些食品分类中使用

- **语义**：表 A.1 中该添加剂对应的所有「使用范围」行。
- **图操作**：从该 `faid` 的 Additive 节点出发，沿 **USED_IN** 出边遍历到所有 Category，并读取边上的属性（maxUsage、remark、usageType 等）。
- **Cypher 示例**：
  ```cypher
  MATCH (a:Additive {faid: $faid})-[r:USED_IN]->(c:Category)
  RETURN a, r, c
  ```
- **API**：`GET /api/additives/{faid}`，返回该添加剂基本信息 + 所有「使用范围」列表（食品分类号、名称、最大使用量、备注等）。

### 3.2 按食品分类查：该分类下允许使用哪些添加剂

- **语义**：该食品分类下允许使用的全部添加剂及各自的使用规定（表 A.1 中所有指向该分类或因其层级而适用的行，在本项目中已预先展开为多条边）。
- **图操作**：从该 `categoryCode` 的 Category 节点出发，沿 **USED_IN** 入边遍历到所有 Additive，并读取边属性。
- **Cypher 示例**：
  ```cypher
  MATCH (c:Category {categoryCode: $code})<-[r:USED_IN]-(a:Additive)
  RETURN a, r
  ORDER BY a.nameCn
  ```
- **API**：`GET /api/categories/{code}`，返回该分类信息 + 该分类下所有添加剂及各自 maxUsage、remark、usageType 等。

### 3.3 交叉查询的本质：同一张图、两种遍历方向

- **同一份数据**：图里只有「添加剂 – USED_IN – 分类」边；每条边表示「某添加剂在某分类下有一条使用规定」。
- **按添加剂查**：以 Additive 为起点，沿 USED_IN **出边** → 得到「该添加剂在哪些分类可用」。
- **按分类查**：以 Category 为起点，沿 USED_IN **入边** → 得到「该分类下有哪些添加剂可用」。
- 两种查询是对同一批边的**反向遍历**，因此按添加剂汇总出的「可用分类」与按分类汇总出的「可用添加剂」在数据一致的前提下是**闭环对应**的。

## 四、标准中的层级与「继承」关系

### 4.1 标准中的规定

GB 2760 中食品分类呈**树状层级**（如 01.0 → 01.05 → 01.05.03）。标准规定：若某添加剂被允许用于某一食品类别，则**在该类别下的所有子类别中均允许使用**，除非子类别有更严或另行规定。因此存在事实上的「继承」：子类继承父类的允许使用范围。

### 4.2 图库中是否存储「继承」或「层级」

- **不存储**。图库中只有：
  - Additive 节点、Category 节点；
  - USED_IN 边（添加剂 → 分类），边上带使用量、备注等。
- 没有「Category –[:PARENT_OF]–> Category」或「limit_id / 父分类」等层级结构；也没有在边上标注「该条规定来自本级 / 上级 / GMP」。

也就是说：**层级与继承关系没有在图数据库中显式建模**，图里存的是「已经按标准规则展开后的 (添加剂, 分类) 使用关系」。

### 4.3 「本级 / 上级 / 适量使用」从哪里来

参考站 2760.foodmate.net 的「使用规则详情」页（如 `category/limit/19.html`）会列出三张表：

- **本级允许使用的添加剂**：表 A.1 中**直接写在该分类号下**的条款。
- **上级允许使用的添加剂**：表 A.1 中写在该分类的**父级分类**下的条款，因层级继承而适用于本分类。
- **对照 A.2 表可以适量使用的食品添加剂**：表 A.2 中「按生产需要适量使用」的添加剂中，适用于本分类的部分。

这三类的**自动研判**不是在当前图数据库中完成的，而是在**数据准备阶段**完成的：

1. **抓取 limit 页**（`fetch_category_usage_details.py`）：对每个分类的 `category/limit/{limit_id}.html` 抓取 HTML，页面中**已经按上述三类排好三张表**（参考站后端已做过层级与 A.2 的解析）。
2. **解析三张表**：按表格出现顺序，将三张表分别解析为 `additives_direct`、`additives_parent`、`additives_gmp`，并为每条添加剂记录打上 **source**：`direct` / `parent` / `gmp`。
3. **生成按分类的索引**（`build_category_usage_with_types.py` 等）：在生成 `category_usage_for_query.json`（以及数据集中的 `index/by_category.json`）时，为每条添加剂保留 **source** 字段。

因此：

- **层级关系自动研判**：由参考站 2760.foodmate.net 在其后端完成（根据分类树与表 A.1/A.2 生成三张表）；我们通过**解析其 limit 页**得到「本级 / 上级 / GMP」的划分，并写入 `by_category` 索引。
- **图库**：只导入扁平表 `additive_usage.json`，不包含 source；因此图库中**无法**按「本级 / 上级 / GMP」分组展示。若需在前端或 API 中还原三张表，需要依赖带 **source** 的索引（如 `index/by_category.json`），而不是图库。

## 五、数据流与职责划分小结

| 环节 | 内容 | 是否在图库 |
|------|------|-------------|
| 添加剂–分类使用关系（扁平） | additive_usage.json → USED_IN 边 | ✅ 是 |
| 按添加剂查「在哪些分类可用」 | 从 Additive 沿 USED_IN 出边 | ✅ 图库 |
| 按分类查「有哪些添加剂可用」 | 从 Category 沿 USED_IN 入边 | ✅ 图库 |
| 分类树 / 父分类 | categories 含 parent_category_code；导入时建 BELONGS_TO 边 | ✅ 图库存层级 |
| 本级 / 上级 / GMP（source） | 来自 limit 页解析，写入 additive_usage 与 USED_IN 边 | ✅ 图库存，可分组展示 |

按分类查询时，API 已支持按 **source** 分组返回：`GET /api/categories/{code}` 返回的 `CategoryDetailDto` 中除 `additives` 外，还包含 **directAdditives**、**parentAdditives**、**gmpAdditives** 三个列表，前端可直接按「本级允许」「上级允许」「适量使用」三张表展示。

## 六、Cypher 查询示例汇总

```cypher
// 按添加剂查使用范围
MATCH (a:Additive {faid: 1})-[r:USED_IN]->(c:Category)
RETURN c.categoryCode, c.categoryName, r.maxUsage, r.remark, r.usageType
ORDER BY c.categoryCode;

// 按分类查可用添加剂
MATCH (c:Category {categoryCode: "01.05.03"})<-[r:USED_IN]-(a:Additive)
RETURN a.faid, a.nameCn, a.function, r.maxUsage, r.remark, r.usageType
ORDER BY a.nameCn;

// 统计某添加剂适用的分类数
MATCH (a:Additive {faid: 1})-[:USED_IN]->(c:Category) RETURN count(c) AS categoryCount;

// 统计某分类下允许的添加剂数
MATCH (c:Category {categoryCode: "01.05.03"})<-[:USED_IN]-(a:Additive) RETURN count(a) AS additiveCount;
```

## 七、层级关系的存储（可实现）

当前图库**未**存储分类之间的父子/层级；若要支持「上级分类」「从根到叶的路径」等查询，可以**增加层级存储**，有两种常见做法。

### 7.1 方案一：Category 之间建关系 BELONGS_TO

- **关系**：`(子分类)-[:BELONGS_TO]->(父分类)`，即子指向父。  
  例如：`(01.05.03)-[:BELONGS_TO]->(01.05)-[:BELONGS_TO]->(01.0)`。
- **父分类推导**：由 `category_code` 推出父节点（只保留最后一段前的内容，若无则无父）：
  - `01.05.03` → 父 `01.05`
  - `01.05` → 父 `01.0`
  - `01.0` → 无父（根）
- **导入时**：在创建完 Category 节点后，按上述规则为每个有父的 code 创建一条从该 Category 指向父 Category 的 BELONGS_TO 边。
- **查询示例**：
  ```cypher
  // 某分类的所有上级（到根）
  MATCH (c:Category {categoryCode: "01.05.03"})-[:BELONGS_TO*]->(ancestor:Category)
  RETURN ancestor.categoryCode, ancestor.categoryName
  ORDER BY ancestor.categoryCode;
  ```

### 7.2 方案二：Category 节点增加属性 parentCategoryCode

- **属性**：在 Category 上增加 `parentCategoryCode`（字符串，可为空）。  
  例如：`01.05.03` 的 parentCategoryCode 为 `"01.05"`，`01.0` 为 null。
- **推导规则**：与上相同，由 code 字符串截取得到父 code。
- **查询示例**：
  ```cypher
  // 某分类的父分类
  MATCH (child:Category {categoryCode: "01.05.03"})
  MATCH (parent:Category {categoryCode: child.parentCategoryCode})
  RETURN parent;
  ```

### 7.3 实现要点

- 父 code 推导逻辑一致：对 `category_code` 按层级分隔符（如 `.`）去掉最后一段，得到父 code；若只剩一段（如 `01.0` 的 `01`）则视业务决定是否再往上（如 `01.0` 无父）。
- 数据来源：`entities/categories.json` 已有全部 category_code，无需新数据，只需在导入脚本中增加「建 PARENT_OF 边」或「写 parentCategoryCode」即可。
- 若同时需要「本级/上级/GMP」分组：层级只解决「谁是谁的上级」；某条添加剂在某分类是 direct/parent/gmp 仍依赖 limit 页解析得到的 **source**，可继续用索引或在 USED_IN 上增加 `source` 属性配合层级使用。

以上说明了图数据库如何存储 GB 2760 使用关系、单位信息与关系属性的关系、如何做双向查询、与标准中层级/继承的关系，以及「本级/上级/GMP」的来源；并说明了**层级关系可以如何存储与查询**。
